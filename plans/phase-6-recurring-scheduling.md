# Phase 6 — Recurring Patients, Followups, and Session-Capacity Scheduling

## Context

Confirmly's current data model only supports one-off, manually-entered appointments (`packages/db/prisma/schema.prisma`). Two real clinic patterns aren't representable today:

1. **Recurring-cadence patients** (e.g. ortho brace patients need a visit every 2-3 weeks, or on a fixed day-of-month, indefinitely). Right now staff would have to manually re-enter a new appointment every single cycle forever — exactly the manual burden Confirmly exists to remove.
2. **Session-based (no fixed time) clinics**: some clinics don't schedule exact appointment times at all — they run "Morning" and "Afternoon" sessions, first-come-first-served, capped at a max number of patients per session. The current model assumes every appointment has an exact `startsAt`/`endsAt` and enforces no-overlap via a DB exclusion constraint, which doesn't fit this pattern at all.

A third, much smaller gap: **one-time followup visits** (e.g. tooth removal → followup checkup) currently have no way to be linked to the visit that prompted them — they're just an ordinary appointment, but staff/patients lose the "this is a followup to X" context.

A fourth gap, surfaced during review: **there is no standalone way for staff to create or browse clients today.** `Patient` records are only ever created implicitly as a side effect of typing a name+phone into the appointment-booking form (`apps/web/components/calendar/AppointmentForm.tsx`) or the waitlist form (`apps/web/app/dashboard/waitlist/page.tsx`), both of which call the existing find-or-create endpoint (`POST /patients` → `patientsService.findOrCreatePatient`, `apps/api/src/routes/patients.ts`). There is no patients list page and no explicit "add client" action independent of booking. Since recurrence rules are set up per-patient (§5's planned patient detail page), staff need a real entry point to reach a patient without first creating a throwaway appointment — this plan adds a dedicated Patients page as a result.

This plan adds all three, sequenced smallest/lowest-risk first, without disturbing the existing reminder pipeline, waitlist (reactive fill-on-cancellation, unrelated to this work), or inbound-SMS confirm/cancel flow — all of which continue to operate unchanged against plain `Appointment` rows.

**Confirmed product decisions (do not re-litigate during implementation):**
- Recurrence rule types: fixed presets only — "every N weeks" or "day X of every month." No general RRULE-style engine.
- Recurring appointments are auto-generated by the system in `scheduled` status (not staff-picked each cycle) — the existing reminder/confirm-reply SMS flow is what confirms the date with the patient, unchanged.
- The next occurrence's date is computed from the **actual completed visit's date**, not calendar drift from the original rule start.
- **No-show pauses the rule** — staff must manually resume it (a call-the-patient-first workflow), rather than silently continuing the cadence.
- **One active recurrence rule per patient** for v1 (creating a second requires pausing/cancelling the first).
- Followups are just a normal `Appointment` with an optional link back to the originating appointment — no new scheduling logic.
- Session-capacity mode is a per-clinic setting (clinic picks once, not per-appointment). Patients/staff pick date + AM or PM; each clinic configures independent max-capacity per session. Appointments in this mode still get `startsAt`/`endsAt` populated to the session's boundary (so existing reminder/query code keeps working), but capacity — not time-overlap — is the actual booking gate, and all patient/staff-facing text shows "Morning"/"Afternoon," never a clock time.

## 1. Schema changes (`packages/db/prisma/schema.prisma`)

### 1a. Followup linkage (self-relation, additive)
```prisma
model Appointment {
  ...
  followUpOfAppointmentId String?       @map("follow_up_of_appointment_id")
  followUpOfAppointment   Appointment?  @relation("AppointmentFollowUp", fields: [followUpOfAppointmentId], references: [id])
  followUps               Appointment[] @relation("AppointmentFollowUp")
  ...
  @@index([followUpOfAppointmentId])
}
```
Display-only — no cascade/deletion concerns since appointments are never hard-deleted (`cancelAppointment` only flips status).

### 1b. Recurrence rule — new model
```prisma
enum RecurrenceRuleType {
  every_n_weeks
  day_of_month
}

enum RecurrenceRuleStatus {
  active
  paused
  cancelled
}

model RecurrenceRule {
  id              String               @id @default(cuid())
  clinicId        String               @map("clinic_id")
  patientId       String               @map("patient_id")
  resourceId      String?              @map("resource_id")
  ruleType        RecurrenceRuleType   @map("rule_type")
  intervalWeeks   Int?                 @map("interval_weeks")     // set iff ruleType = every_n_weeks
  dayOfMonth      Int?                 @map("day_of_month")       // 1-31, set iff ruleType = day_of_month
  durationMinutes Int                  @default(30) @map("duration_minutes") // fixed-time mode only
  sessionOfDay    SessionOfDay?        @map("session_of_day")     // session-capacity mode only
  status          RecurrenceRuleStatus @default(active)
  notes           String?
  createdAt       DateTime             @default(now()) @map("created_at")
  updatedAt       DateTime             @updatedAt @map("updated_at")

  clinic       Clinic        @relation(fields: [clinicId], references: [id])
  patient      Patient       @relation(fields: [patientId], references: [id])
  appointments Appointment[]

  @@index([clinicId, patientId])
  @@map("recurrence_rules")
}
```
Add to `Appointment`: `recurrenceRuleId String? @map("recurrence_rule_id")` + relation + `@@index([recurrenceRuleId])`.

`intervalWeeks`/`dayOfMonth` mutual-exclusivity by `ruleType` is validated at the zod route layer (matches this codebase's existing pattern — no DB CHECK constraints exist beyond the one exclusion constraint). Enforce "one active rule per patient" in the service layer (`createRecurrenceRule` checks for an existing `active` rule for that patient and rejects/errors if found), not via a DB unique constraint (status is mutable, a partial unique index on `status='active'` is possible but adds migration complexity for marginal benefit at this scale — plain service-layer check is enough).

### 1c. Clinic scheduling mode + session capacity
```prisma
enum SchedulingMode {
  fixed_time
  session_capacity
}

enum SessionOfDay {
  am
  pm
}

model Clinic {
  ...
  schedulingMode     SchedulingMode @default(fixed_time) @map("scheduling_mode")
  sessionCapacityAm  Int?           @map("session_capacity_am")
  sessionCapacityPm  Int?           @map("session_capacity_pm")
  sessionAmStartHour Int            @default(8)  @map("session_am_start_hour")
  sessionAmEndHour   Int            @default(12) @map("session_am_end_hour")
  sessionPmStartHour Int            @default(13) @map("session_pm_start_hour")
  sessionPmEndHour   Int            @default(18) @map("session_pm_end_hour")
}
```
Add to `Appointment`:
```prisma
  sessionOfDay      SessionOfDay? @map("session_of_day")
  isSessionCapacity Boolean       @default(false) @map("is_session_capacity")
```
`isSessionCapacity` is stamped at creation time from the clinic's current mode — this is what makes the exclusion constraint scoping below possible without a cross-table lookup in a WHERE clause.

### 1d. Exclusion constraint must be scoped to fixed-time appointments only

In session-capacity mode, multiple appointments in the same AM session share identical `startsAt`/`endsAt` (both = the session boundary) — under the current constraint this would always collide, which is wrong (capacity, not overlap, is the gate). Migration:
```sql
ALTER TABLE "appointments" DROP CONSTRAINT "appointments_no_overlap";
ALTER TABLE "appointments" ADD CONSTRAINT "appointments_no_overlap" EXCLUDE USING gist (
    "clinic_id" WITH =,
    COALESCE("resource_id", '') WITH =,
    tstzrange("starts_at", "ends_at") WITH &&
) WHERE (status NOT IN ('cancelled', 'no_show') AND is_session_capacity = false);
```
Fixed-time clinics keep byte-for-byte identical overlap protection. Session-capacity rows are fully exempted; capacity enforcement (below) is the real gate for them.

### 1e. Atomic capacity enforcement

Naive count-then-insert is a TOCTOU race (two staff booking the last AM slot simultaneously must not both succeed). Use a Prisma `$transaction` with `Serializable` isolation that counts active appointments for that clinic/date/session and inserts only if under capacity, catching Postgres serialization-failure SQLSTATE `40001` the same way `isExclusionViolation` already catches `23P01` in `apps/api/src/services/appointments.ts:30-38` — same pattern, new sibling error class `SessionFullError`.

## 2. Services (`apps/api/src/services/`)

**`recurrence.ts` (new)**
- `createRecurrenceRule(params)` — validates rule-type field presence, rejects if patient already has an `active` rule, creates the row, and immediately generates the first appointment (so staff see it appear right away, not after a delay).
- `computeNextOccurrence(rule, fromDate)` — pure cadence math: `every_n_weeks` → `fromDate + N*7d`; `day_of_month` → next month's `dayOfMonth`, clamped to that month's last day if it doesn't have that many days (e.g. day 31 in Feb → Feb's last day).
- `generateNextAppointmentForRule(ruleId)` — finds the rule's most recent appointment by `startsAt`, computes the next date from **that appointment's actual `startsAt`** (not the rule's original start date — avoids drift from reschedules), creates a new `Appointment` with `recurrenceRuleId` set and status `scheduled`, dispatching to the fixed-time or session-capacity booking path per the clinic's current `schedulingMode`.
- `pauseRecurrenceRule` / `resumeRecurrenceRule` / `cancelRecurrenceRule` / `listRecurrenceRulesForPatient`.

**Extend `appointments.ts`** — in `updateAppointment`, when a status transition lands on:
- `completed` (with a non-null `recurrenceRuleId`): call `recurrenceService.generateNextAppointmentForRule`.
- `no_show` (with a non-null `recurrenceRuleId`): call `recurrenceService.pauseRecurrenceRule` instead — per confirmed decision, no-show pauses the cadence rather than continuing it.

This mirrors the existing pattern where `cancelAppointment`'s route handler already triggers `waitlistService.checkWaitlistFill` synchronously as a side effect of a status change (`apps/api/src/routes/appointments.ts`) — no new architecture, just one more side effect on the same write path.

**`sessions.ts` (new)** — `bookSessionCapacitySlot({ clinicId, patientId, date, sessionOfDay, resourceId? })`: computes `startsAt`/`endsAt` from the clinic's session-hour settings, runs the Serializable count-check-insert transaction from §1e, sets `isSessionCapacity: true`. Kept as a separate service rather than branching inside `createAppointment`, since the booking gate (capacity count) is a genuinely different code path from the exclusion-constraint-catch path.

**Waitlist**: no changes. `checkWaitlistFill` already operates generically on any appointment's `clinicId/resourceId/startsAt/endsAt` and fires unchanged whether the cancelled/no-show appointment came from a recurrence rule or was booked manually.

## 3. Jobs

**No new cron job.** Recurrence generation is triggered synchronously on the `completed`/`no_show` status transition (§2), not polled. `reminder-dispatch.ts`'s hourly cron exists because its trigger is time itself ("has lead time elapsed"), which has no discrete event to hook into — recurrence generation has a crisp existing event (the status-update route) and hooking into it is simpler than adding a second job, avoids up-to-an-hour delay after a visit is marked complete, and adds zero new infrastructure (consistent with CLAUDE.md's single-instance/no-queue-infra constraint).

Known gap, accepted for v1: if staff never explicitly marks a recurring appointment `completed`, the next occurrence never generates. This matches real clinic workflow (staff already marks visits complete) and isn't solved by a cron job either without speculative "presumed completed" heuristics — not building that preemptively.

## 4. Routes

**Extend `apps/api/src/routes/patients.ts`**: add `GET /patients/:id` (single-patient lookup, scoped by clinic like `getAppointment`'s pattern in `appointments.ts`) and a `POST /patients` explicit-create variant — the existing find-or-create behavior is fine to keep for the booking-form/waitlist-form call sites, but the new standalone "Add client" form (§5) should be able to surface a clear error if a phone number already exists for the clinic (currently find-or-create silently returns the existing record, which is the right UX for "booking an appointment" but wrong for "I'm explicitly adding a new client and typoed the number") — add a `mode: "find_or_create" | "create"` flag or a separate `strict` boolean to `patientsService`, defaulting to today's find-or-create behavior so existing call sites need no changes.

**`apps/api/src/routes/recurrence.ts` (new)**, behind existing `requireAuth`, scoped by clinic like all other routes:
- `POST /patients/:patientId/recurrence-rules` — create.
- `GET /patients/:patientId/recurrence-rules` — list.
- `PATCH /recurrence-rules/:id` — pause/resume/cancel/edit cadence.

**Extend `apps/api/src/routes/appointments.ts`**: add `followUpOfAppointmentId: z.string().min(1).nullable().optional()` to the existing create schema — no new endpoint needed.

**Extend `apps/api/src/routes/clinic-settings.ts`**: add `schedulingMode`, `sessionCapacityAm/Pm`, and the four session-hour fields to the GET response and PATCH schema — mechanical extension of the existing flat pass-through pattern.

**`POST /appointments`**: route handler checks `clinic.schedulingMode` and dispatches to `appointmentsService.createAppointment` (fixed-time) or `sessionsService.bookSessionCapacitySlot` (session-capacity) — body shape differs (`startsAt`/`endsAt` vs `date`+`sessionOfDay`), expressed as a zod discriminated union.

**`patient-session.ts`**: `buildAvailableSlots` needs a session-capacity branch returning "AM has N remaining / PM has M remaining" per day instead of discrete timestamps.

## 7. Build sequencing

1. **Patients list + detail page** — prerequisite for recurring patients (staff need somewhere to set up a rule without first faking an appointment) and useful on its own regardless of the other features. Small: the API's find-or-create/list already exist, this is mostly new frontend plus one new `GET /patients/:id` route. Build first.
2. **Followups** — trivial, one nullable FK + one form field + one line of display text, zero interaction with the other features. Low-risk, can be done in parallel with/immediately after step 1.
3. **Recurring patients** — self-contained (one new model, one new service, one trigger point in an existing route), no new concurrency pattern, uses the patient detail page from step 1 for its UI. Lower risk than session-capacity mode despite being "more involved."
4. **Session-capacity mode** — requires a new concurrency-control pattern (Serializable transaction + retry, no precedent in this codebase yet) and a new dashboard view + patient-facing slot-picker variant. Larger surface area; per CLAUDE.md's "don't build ahead of pilot validation," worth confirming with the pilot/target clinics that they actually run session-based (not fixed-time) scheduling before investing here.

Steps 2-4 are technically independent of each other (no hard dependency forces one before another beyond step 1 being a prerequisite for step 3) — the sequencing above is a risk/validation call, not a technical constraint.
